## 1. Product Architecture

### 1.1 Core concept

StudyPilot is **not** a calendar or todo list. A todo list records what you intended to do; a calendar records what you *should* have done. StudyPilot's differentiator is that **the plan is a function of reality** — when the student actually does less than planned, the plan re-derives itself from current time, remaining workload, energy, and confidence.

### 1.2 Layered architecture

The system is split into four layers with a strict one-way dependency rule: **UI → Application → Domain → Infrastructure**. Domain logic never imports from UI or infrastructure, which is what makes it unit-testable without a database or browser.

```
┌─────────────────────────────────────────────────────────┐
│  UI LAYER — app/ (RSC pages, client islands, components)│
│  Renders state. Holds no business rules.                 │
└────────────────────────┬────────────────────────────────┘
                         │ calls
┌────────────────────────▼────────────────────────────────┐
│  APPLICATION LAYER — lib/actions/, lib/queries/         │
│  Orchestration: auth check → validate → engine → persist │
│  Owns transactions and revalidation.                    │
└────────────────────────┬────────────────────────────────┘
                         │ calls
┌────────────────────────▼────────────────────────────────┐
│  DOMAIN LAYER — lib/domain/  ← PURE TYPESCRIPT          │
│  Scheduler, Plan Rescue, Memory Radar, Difficulty Debt, │
│  Study Now. Deterministic. No I/O. No React. No DB.     │
└────────────────────────┬────────────────────────────────┘
                         │ reads/writes via interface
┌────────────────────────▼────────────────────────────────┐
│  INFRASTRUCTURE — lib/supabase/, lib/openai/            │
│  Supabase clients, OpenAI client, env access.            │
└─────────────────────────────────────────────────────────┘
```

### 1.3 The critical decision: domain logic is pure and deterministic

**This is the single most important architectural decision in the project.**

All five core features are expressed as **pure functions** in `lib/domain/` that take plain data structures and return plain data structures. They perform no network calls, touch no database, and import nothing from React or Supabase.

```
planRescue(plan, missedSessions, availability, now) → newPlan
memoryRadar(topics, reviews, now)                    → riskScores[]
difficultyDebt(topics, exams, sessions, now)        → debtScores[]
studyNow(plan, radar, debt, energy, now)            → oneSession | null
generateInitialPlan(subjects, exams, availability,
                    energy, now)                     → plan
```

## 4. Database Architecture

Supabase PostgreSQL, managed, with migrations versioned in the repository under `supabase/migrations/`.

### 4.1 Core principle: multi-tenant isolation via `user_id`

Every table owned by a student carries a `user_id` column referencing `auth.users(id)`. Combined with **Row Level Security (RLS)**, a student can only ever see and modify their own rows — enforced **by the database**, not by application code.

**Why this matters:** application-level checks ("is this my session?") are one forgotten `if` away from a data leak. RLS policies live in the database and apply to *every* query path, including a buggy one written six months from now. It is the safety net under the application.

### 4.2 Schema

```sql
-- Auto-create a profile row whenever a user signs up
create or replace function public.handle_new_user()
returns trigger language plpgsql security definer as $$
begin
  insert into public.profiles (id, email)
  values (new.id, new.email);
  return new;
end; $$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

| Table | Key columns | Purpose |
| --- | --- | --- |
| `profiles` | `id` (PK → auth.users), `email`, `full_name`, `timezone`, `onboarding_completed`, `daily_study_goal_minutes` | One row per user, auto-created at signup |
| `subjects` | `id`, `user_id`, `name`, `color`, `difficulty` (1–5) | A subject, e.g. "Calculus" |
| `topics` | `id`, `user_id`, `subject_id` (FK), `name`, `estimated_minutes`, `difficulty` (1–5), `confidence` (0–100), `last_reviewed_at` | A unit within a subject; the atom of scheduling |
| `exams` | `id`, `user_id`, `subject_id` (FK), `title`, `exam_date`, `importance` (1–5) | Drives urgency weighting |
| `availability_windows` | `id`, `user_id`, `day_of_week` (0–6), `start_time`, `end_time` | Recurring "I'm free then" blocks |
| `energy_preferences` | `id`, `user_id`, `time_block`, `label`, `energy_level` (1–5) | Maps hours of the day → focus level (BrainFit) |
| `study_plans` | `id`, `user_id`, `name`, `is_active`, `generated_at`, `generation_reason` | A plan version; regenerating creates a new one rather than destroying history |
| `study_sessions` | `id`, `user_id`, `plan_id` (FK), `topic_id` (FK), `scheduled_start`, `scheduled_end`, `actual_minutes`, `status` (`planned`/`completed`/`skipped`/`rescheduled`), `energy_match` | The concrete scheduled work units |
| `topic_reviews` | `id`, `user_id`, `topic_id` (FK), `reviewed_at`, `confidence_after` (0–100), `recalled_correctly` | Append-only review log — the raw data Memory Radar learns from |

### 4.3 Design decisions worth explaining

- **`confidence` on `topics` is the current belief; `topic_reviews` is the history.** Keeping both lets us show a trend line *and* compute forgetting risk, without rewriting the topic row on every review.
- **`study_plans` are versioned, not overwritten.** When Plan Rescue runs, it marks the old plan inactive and creates a new one. This gives an audit trail ("what did the plan look like before I missed three days?") and makes the algorithm debuggable after the fact.
- **`status` is a `text` column with a `check` constraint**, not a Postgres `enum` type. Adding a status later then requires only an `alter constraint`, not a type migration.
- **Timestamps are `timestamptz`.** A student in another timezone must see correct times; `profiles.timezone` (IANA string) drives display conversion.
- **Indexes on `(user_id)` and common filter columns** such as `study_sessions(scheduled_start, status)` — the dashboard queries by user and time range on every load.

### 4.4 RLS — enabled on every table

Every table gets RLS enabled, with policies of the form:

```sql
alter table public.study_sessions enable row level security;

create policy "Users can manage their own sessions"
  on public.study_sessions
  for all
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

Note `with check` as well as `using`: `using` controls who can *read/update/delete* existing rows, while `with check` prevents a student from *inserting* a row belonging to someone else. Omitting `with check` is a classic privilege-escalation bug.

Server-side writes use the service-role key, which bypasses RLS — so **every Server Action must verify ownership in code as well.** RLS is the safety net; the application check is the primary defence. Both layers are required.

## 5. Authentication Architecture

### 5.1 Approach

**Supabase Auth** (email + password first; OAuth providers added only if requested later). No custom password handling, no hand-rolled JWTs, no fake/mock auth of any kind.

Three separate concerns, deliberately kept distinct:

| Concern | Question | Mechanism |
| --- | --- | --- |
| **Authentication** | *Who are you?* | Supabase Auth issues a signed session, stored in cookies |
| **Session management** | *Are you still logged in?* | `@supabase/ssr` reads/refreshes the cookie per request |
| **Authorization** | *What may you access?* | Layout guard + per-action check + RLS |

### 5.2 The session chokepoint

```ts
// lib/supabase/server.ts
import { createServerClient } from '@supabase/ssr'
import { cookies } from 'next/headers'

export async function createClient() {
  const cookieStore = await cookies()   // Next 16: async API
  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    { cookies: { getAll, setAll } }     // refreshed token written back here
  )
}
```

**Why cookies rather than `localStorage`:** localStorage is readable by any JavaScript on the page, so an XSS bug becomes a full account takeover. `HttpOnly` cookies are invisible to JavaScript entirely. This is the single most important security decision in the auth layer.

### 5.3 Route protection — defence in depth

Three independent layers, because any one of them can fail:

1. **`proxy.ts`** (Next 16's replacement for `middleware.ts`) — refreshes the Supabase session cookie on every request and does a **fast optimistic redirect** for unauthenticated users hitting `/dashboard`.
2. **`app/(app)/layout.tsx`** — the authoritative check. Calls `supabase.auth.getUser()` and `redirect('/login')` if absent. This is the real gate; the proxy only improves perceived speed.
3. **Every Server Action** — re-verifies the session and resource ownership *inside* the action.

**Critical rule:** `proxy.ts` and layouts are **user-experience layers, not the security boundary.** Server Functions are reachable by direct `POST` request, not just through our UI. A malicious user can craft a raw POST to any action endpoint. Therefore **every single Server Action begins with a session check and an ownership check**, without exception.

### 5.4 Server Actions are not implicitly trusted

```
POST arrives -> "use server" function runs on server
             -> await supabase.auth.getUser()      <- MUST be first
             -> validate input shape                <- never trust FormData
             -> verify row belongs to this user     <- ownership
             -> run domain engine / write to DB
             -> revalidatePath(...)
             -> return { ok: true } or { ok: false, error: "..." }
```

Every action returns a **discriminated result object** rather than throwing, so the UI can render a real message. Genuine unexpected errors propagate to `error.tsx` and are logged — never silently caught.

## 6. Data Flow

### 6.1 Reading data (Server Component render)

```
Browser requests /dashboard
  -> Next.js server renders app/(app)/dashboard/page.tsx
     -> await createClient()            // reads session cookie
     -> await supabase.auth.getUser()   // confirms the session is real
     -> redirect('/login') if missing   // protection lives here
     -> fetch subjects, exams, sessions // queries scoped to this user
     -> compute radar / debt / study-now with PURE domain functions
     -> render HTML on the server
  -> browser receives finished HTML (minimal JS)
```

Data is fetched on the server so nothing sensitive or unnecessary is shipped to the browser, and the user sees content immediately rather than a spinner followed by content.

### 6.2 Writing data (Server Action mutation)

```
User submits a form
  -> React calls the Server Action (POST under the hood)
     -> await supabase.auth.getUser()          // step 1: who?
     -> validate the payload shape              // step 2: sane input?
     -> fetch the row, check it belongs to user // step 3: yours?
     -> run the domain engine (pure)            // step 4: decide
     -> write to Postgres                       // step 5: persist
     -> revalidatePath('/dashboard')            // step 6: refresh cache
     -> return { ok: true } | { ok: false, error }
  -> useActionState re-renders with fresh server data
```

## 8. Testing Strategy

### 8.1 Layered approach (cheapest and most valuable first)

| Layer | Tool | What it covers |
| --- | --- | --- |
| **Types** | `tsc --noEmit` | Whole codebase, every build. Catches the most errors. |

| **Build** | `next build` | Compiles and statically renders every route |
| **Manual UAT** | Checklist | Flow and visual review |

### 8.2 Why unit tests target `lib/domain/`

Because those functions are **pure**, they are trivially testable with no database, no network, and no browser. They are also where a bug is most costly and most invisible: a scheduling bug might not crash — it would just quietly produce a bad study plan, which is the one thing this product promises not to do.

```ts
// example shape, written when Phase 6 lands
it('spreads missed work without exceeding daily capacity', () => {
  const result = planRescue(plan, missedSessions, availability, now)
  expect(result.sessions.every(s => s.durationMinutes <= 120)).toBe(true)
  expect(totalMissedMinutes(result)).toEqual(totalMissedMinutes(plan))
})
```

That second assertion matters: redistributed work must be **conserved**, not lost or duplicated.

### 8.3 What we deliberately do NOT test yet

- **No Playwright/Cypress in early phases.** End-to-end tests are slow and brittle, and there is little real behaviour to exercise while pages are static. Revisit in Phase 12 when the flows are stable.
- **No snapshot testing.** Large snapshots are noisy and produce false confidence; asserting specific values is more useful.
- **No mocking of the database.** Once Supabase is live, tests use a real test project — because mocking a database tests the mock, not the app.

## 9. Security Strategy

### 9.1 Principles

1. **The database is the security boundary.** RLS applies to every query path, including a buggy one written months from now. Application-level checks are the first line, not the only line.
2. **Never trust the client.** Form data is user input. Validate shape and bounds in every Server Action.
3. **Never trust the network.** Anything arriving at a Server Action could have been crafted by hand.
4. **Fail closed.** On any uncertainty — session check fails, RLS errors — deny access rather than allow it.

### 9.2 Controls in place

| Risk | Control |
| --- | --- |
| Cross-user data access | RLS on every table + ownership check in every action |
| Session theft via XSS | `HttpOnly` cookies (not `localStorage`) |
| Secret leakage to browser | No-prefix env vars are server-only; build fails if referenced in client code |
| Secrets in version control | `.env*` gitignored; `.env.example` committed with empty values |
| SQL injection | Supabase client parameterises queries; no string-built SQL |
| XSS | React escapes by default; no `dangerouslySetInnerHTML` anywhere |
| CSRF | Server Actions verify Origin; SameSite cookies |
| Privilege escalation via insert | RLS `with check` clause on write policies |
| Open redirect | Only internal, validated redirect targets |
| Abuse of OpenAI | Server-only call, per-user rate limit, input length cap |

### 9.3 Rule compliance

| Rule | How it is enforced |
| --- | --- |
| #9 Never hide errors | `error.tsx` + `ErrorState`; real messages to users, real logs to dev; no empty `catch {}` |
| #11 No fake functionality | Every mock-data surface carries a visible `MockDataNotice`; disabled controls instead of no-ops |
| #12 No fake auth | Forms are explicitly `disabled` with a "not connected yet" notice — they never pretend to sign in |
| #13 No fake persistence | No localStorage/JSON persistence anywhere; mock data is a static file, not a fake database |
| #14–16 Env vars only | Secrets from `process.env` only; see §5.5 |

## 10. Deployment Strategy

### 10.1 Platform

**Vercel**, connected to the GitHub repository. Push to `main` -> automatic production deploy. Preview deploys for every other branch, which gives free staging environments.

Vercel is the natural fit because the app is a Next.js project with server-side data fetching — the same runtime we develop against locally, so there is no "works on Vercel but not on my machine" class of problem.

### 10.2 Workflow

```
feature branch -> push -> Vercel preview URL -> review -> PR -> main -> production
```

### 10.3 Environment variables on Vercel

Set in **Project Settings > Environment Variables** (never in a committed file):

| Variable | Scope | Notes |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | All | Public |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | All | Public, RLS-protected |
| `SUPABASE_SERVICE_ROLE_KEY` | All | **Secret** — server only |
| `OPENAI_API_KEY` | All | **Secret** — server only |

Scope each variable to the right environments; Preview may use a separate Supabase project so testing never touches production data.

### 10.4 Deployment phases

- **Phases 1–2:** deploy early, even with mock data. It validates the pipeline while risk is low.
- **Phase 12:** final production hardening, custom domain, error monitoring, database backups.

### 10.5 CI

A GitHub Actions workflow runs `tsc --noEmit`, `npm run lint`, and `npm run build` on every push and PR. **A red CI blocks merge** — this is what stops a broken commit reaching production.

## 11. Risks and Technical Decisions

### 11.1 Key decisions and their reasoning

| Decision | Reasoning | Trade-off accepted |
| --- | --- | --- |
| **Pure domain functions** | Deterministic, testable without a database, debuggable | Extra indirection; data must be fetched before computing |
| **No ORM** | Supabase's typed client + generated types are sufficient | We write some SQL by hand |
| **No state library** | Server Components + URL state cover our needs; state lives in Postgres | Complex client-side optimistic updates need thought |
| **No UI library** | Tailwind suffices; keeps bundle small and design controlled | We must build and maintain primitives |
| **RLS + app checks** | Two independent layers; either alone can fail | Slightly more code per action |
| **AI last, never authoritative** | App must work with OpenAI down | Less "magic" during early development |
| **`cacheComponents` off** | Every page is per-user and dynamic; enabling adds invalidation risk for no gain | No static optimisation of dashboard pages |
| **Route groups** | Clean URLs, shared layouts, protected-by-default | Folder names differ from URLs |

### 11.2 Risks and mitigations

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| Scheduling produces an unusable or overloaded plan | Medium | **High** — breaks the core promise | Pure functions + unit tests; hard daily-duration ceiling; conservative defaults |
| RLS misconfigured on one table | Medium | **Critical** — data leak | Per-table review; two-account isolation test in Phase 2; test every table |
| A student overloads themselves | Medium | High | Daily study cap; Plan Rescue spreads rather than compresses; "overloaded" warning |
| Plan Rescue schedules work in the past | Low | High | Engine takes `now` as a parameter and never schedules before it |
| Confident but wrong recommendations | Medium | Medium | Show the *reason* behind every recommendation; let students override |
| Timezone bugs across travel/DST | Medium | Medium | `timestamptz` everywhere; store IANA timezone; convert on display only |
| Next.js 16 unfamiliar conventions | Medium | Medium | `AGENTS.md` points to version-matched docs; read before coding |
| Scope creep from AI features | Medium | Medium | AI is Phase 11, explicitly optional, never load-bearing |
| Beginner overwhelmed by codebase size | Low | Medium | Modularity, documented phases, small reviewable commits |

### 6.3 One worked example: completing a session

### 6.4 Caching strategy

Authenticated pages are **per-user**, so they are not cached and shared. `cacheComponents` stays **off**: enabling it would add invalidation complexity with no benefit for data that is unique to one student. Static generation is used only for the public marketing pages.
# for this; RLS is what protects the data.
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=

# NO prefix = server-only. Referencing these from a Client Component fails
# the build, which is exactly the safety we want.
SUPABASE_SERVICE_ROLE_KEY=
OPENAI_API_KEY=
```

**Rule #16 enforced by construction:** any client component referencing `SUPABASE_SERVICE_ROLE_KEY` or `OPENAI_API_KEY` fails to build, because Next.js replaces non-public env vars with `undefined` in browser bundles. The failure is loud, by design.

- All schema lives in `supabase/migrations/NNN_name.sql`, applied in order. **Schema changes go through migrations only** — never by hand-editing the live database.
- `supabase/types.ts` is generated from the live schema and committed, giving the TypeScript client real row types.
- Every migration is backwards-compatible with the currently-deployed code, so deploys never break mid-migration.
